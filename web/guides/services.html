Engines in the background

Every engine xokolat talks to is a server. Once you accept that, the app-with-a-window is the wrong shape for it — you want it running quietly at login, and one command that keeps it current. This page is both halves.

Run it as a service

On macOS the short path is Homebrew. A user service is a launch agent: it starts when you log in, restarts if it dies, and writes its output to a log instead of a terminal you have to keep open.

brew services start comfyui
brew services list
brew services restart comfyui

Not every engine ships a formula. When one doesn't, you write a small one that points at a runner script — a few lines that export the environment and exec the server. That is all the ComfyUI and Draw Things services on this machine are.

Bind to 127.0.0.1 unless you mean otherwise. An engine listening on 0.0.0.0 is reachable by anything on the network, and none of these have authentication. Keep them local, and reach them from another machine over a private network rather than by opening the port.

On Linux the same idea is a systemd user unit (systemctl --user enable --now comfyui). On Windows it is a scheduled task set to run at logon. The mechanism differs; what you want from it does not.

Keep it up to date

This is the half everyone skips, and it fails silently: an engine installed once and never updated keeps working, so nothing tells you it has fallen a year behind — until a workflow needs a node that shipped six months ago.

Nothing else will do it for you. These engines are not packages: your package manager cannot see a git clone in your home directory, and a binary downloaded from a release page is invisible to everything. So give each engine one script that owns its whole update, and have whatever you already run weekly call that.

what one update script does
  1. Note the version that is running now.
  2. Stop the service.
  3. Pull the new code, and reinstall its dependencies.
  4. Start the service and ask it a question — an HTTP request it can only answer if it really came back.
  5. If it doesn't answer, put the old version back and say so loudly.
Ask about the thing you changed, not just whether it is alive. A liveness question — "are you answering?" — cannot see everything an update can break. Install something that makes an engine faster rather than different, and a broken version answers exactly like a working one: the check says all fine, and you find out weeks later from a render that takes an hour. So when an engine gains a capability you care about, the update script gains a question that only a working version can answer.

Step five is the one that matters. Following the tip of a branch means running code nobody has released yet, so eventually a version will not start — and an update that leaves a dead engine behind is worse than no update at all. With a rollback you get the newest code when it works, and last week's when it doesn't.

Two rules that keep an unattended run safe. It must never need sudo — a password prompt in a background job waits forever. And it must be silent when nothing changed but loud when something broke, or you will stop reading the output and never notice the day it stopped working.

Where the scripts live

xokolat ships one per engine it knows, in services/<id>/update.sh inside the app itself, named for the service's id in the inference registry. They come back with any reinstall, so they cannot be lost. To add one for an engine of your own, put it in your data folder under the same shape — a packaged app cannot write to its own install folder, which is what this second layer is for:

~/Library/Application Support/xokolat/services/<id>/update.sh

Same rule as the registries — the same id replaces the shipped script, a new id is added alongside. Then a single line wires the lot into whatever you already run:

[commands]
"xokolat engines" = "<your xokolat folder>/scripts/update-services.sh"

That is one line forever. Adding a fourth engine means dropping in a fourth folder, never editing that config again.

Only ever put a script there by hand. These run unattended, on a schedule, as you. That folder must never be written to by anything arriving over a network — a downloaded workflow, a shared graph, an installer. xokolat never writes there itself.

Models are not part of this

None of it touches checkpoints. Weights are tens of gigabytes, they are yours, and you replace them when you decide a workflow needs something new. An update script that quietly pulled a 40 GB model on a Sunday morning would be a bug.
