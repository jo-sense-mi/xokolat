Draw Things

The image engine xokolat uses today. It is a macOS app with a server inside it, and that server speaks gRPC on port 7859. Two ways to have one answering.

Whichever route you take, the result is identical from xokolat's side: something listening on 127.0.0.1:7859 that can list its checkpoints. The shipped registry row already points there, so there is nothing to configure in the app.

Route A — simplest

Switch the server on inside the app

Install Draw Things, open it, and find the API server section in its settings. Turn it on, set the protocol to gRPC, and leave the port at 7859. Enable the model browser if it is offered — that is how xokolat asks what checkpoints, LoRAs and ControlNets you have.

Then press ↻ on the Draw Things card in xokolat's 🔌 inference page.

The catch: the app has to stay open. Quit it and xokolat's card goes red.

Route B — headless

Run the server on its own, at login

Draw Things publishes a standalone server binary, gRPCServerCLI-macOS, with the releases of its community repository. It serves the same models the app has already downloaded — there is nothing to copy and no second library.

You still want the app installed, because the app is how you download models.

Running it by hand first

Do this once in a terminal before making it permanent. If it does not work here, a launch agent will only make the failure quieter.

./gRPCServerCLI-macOS \
  ~/Library/Containers/com.liuliu.draw-things/Data/Documents/Models \
  --name xokolat \
  --address 127.0.0.1 \
  --port 7859 \
  --no-tls \
  --no-response-compression \
  --model-browser

What each of those is for:

  • The first argument is the models directory, and it is the app's own container path above. Point at it rather than copying anything: everything you download in Draw Things — checkpoints, LoRAs, ControlNets, IP-Adapters — appears to the server immediately.
  • --address 127.0.0.1 — this machine only. Generation is not a thing to put on a network by accident.
  • --no-tls — plaintext, which is what a client on the same machine wants. It is the right choice because of the line above; on any other address it would not be.
  • --no-response-compression — xokolat needs this one. With it the server ships uncompressed float16 pixels, which the client decodes with no extra dependency. Compressed responses use a codec xokolat does not carry.
  • --model-browser — lets a client ask what the server has. Without it xokolat can still render, but its catalog stays empty and every workflow reads as needs 1 thing.
Do not add --echo-on-queue. It routes the discovery call through the same queue as generation, and the queue blocks waiting for the handler that is itself waiting on the queue. Nothing renders again until you restart it. xokolat's health check is a plain TCP probe partly because of this.

Making it survive a reboot

A per-user launch agent: a plist in ~/Library/LaunchAgents/. Save this as ~/Library/LaunchAgents/lat.xoko.draw-things-grpc.plist and replace both YOUs with your short username (id -un prints it) — launchd does not expand ~.

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN"
  "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key>
  <string>lat.xoko.draw-things-grpc</string>
  <key>ProgramArguments</key>
  <array>
    <string>/Users/YOU/bin/gRPCServerCLI-macOS</string>
    <string>/Users/YOU/Library/Containers/com.liuliu.draw-things/Data/Documents/Models</string>
    <string>--name</string><string>xokolat</string>
    <string>--address</string><string>127.0.0.1</string>
    <string>--port</string><string>7859</string>
    <string>--no-tls</string>
    <string>--no-response-compression</string>
    <string>--model-browser</string>
  </array>
  <key>RunAtLoad</key><true/>
  <key>KeepAlive</key><true/>
  <key>StandardOutPath</key>
  <string>/Users/YOU/Library/Logs/draw-things-grpc.log</string>
  <key>StandardErrorPath</key>
  <string>/Users/YOU/Library/Logs/draw-things-grpc.err.log</string>
</dict>
</plist>

Load it:

launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/lat.xoko.draw-things-grpc.plist

To stop it, or to reload after editing the plist:

launchctl bootout gui/$(id -u)/lat.xoko.draw-things-grpc
It must be a user agent. Never sudo, never a LaunchDaemon.

The Metal path this server renders through needs a WindowServer context, and only the logged-in graphical session has one. Run it as root, or from /Library/LaunchDaemons, or from a system service manager, and it starts perfectly, reports no error, accepts requests, and returns pure colourful static — then exits 0.

There is no message anywhere that tells you this. If your renders are noise, this is why. gui/$(id -u) in the commands above is the part that gets it right.

If you would rather use Homebrew

brew services is a friendlier front end to exactly the file above — it writes the same plist into the same folder. If you already keep services that way, use it. Just make sure it is brew services start … as yourself and not sudo brew services, which writes a system daemon and lands you in the trap above.

Checking it worked

nc -z 127.0.0.1 7859 && echo "listening"

Then in xokolat: 🔌 inference → Draw Things → ↻. The card should say reachable and the catalog line should report the number of models it found. Render one picture and look at it — noise means the session trap, not a xokolat problem.

Ports, flags and paths here are what xokolat's shipped registry row expects. If you change the port, change it on the card too — 🔌 inference → the Draw Things card → where it is.
